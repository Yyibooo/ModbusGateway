## 当前链路和边界

两个 TCP 客户端连接网关的 1506 端口。每条连接有自己的前端上下文和请求缓冲区，连接线程把任务提交到有界队列，唯一的后端工作线程依次调用 `modbus_proxy()`。调用结束后，工作线程标记 `job.done = 1`，连接线程再清理任务与前端连接。

[共享后端网关](../gateway_shared_backend_demo.c)传入串口路径时使用 RTU，默认使用 1502 上的 TCP 后端。本阶段的网关一轮接入两个客户端，每条连接处理一条请求。RTU 设备地址为 1，串口参数是 9600 8N1，回归测试使用 socat 虚拟串口。真实 RS-485 硬件、长期运行、重连和配置化属于后续工作。

- 网关打开 `/tmp/modbus-rtu-client`，从站打开 `/tmp/modbus-rtu-server`。从站用可选参数 `2` 处理一写一读，并保留同一张寄存器表。
- TCP 客户端的 Unit ID 由代理传给 RTU 后端作为设备地址。设备地址 1 与设备内部的寄存器地址 1 是两个独立字段。
- libmodbus 3.2.0 安装在 `~/.local/libmodbus-3.2.0`，`make check-modbus` 可验证构建。socat 在 `~/.local/bin/socat`，构建产物统一放在 `build/`。
- `gateway_shared_backend_demo.c` 是当前网关。`modbus_gateway.c` 是早期单客户端代理，其 20 ms 后端响应超时属于单元 10 的演示设置。进入 19 时先核对当前网关的实际超时。
- [examples](../examples/)放早期 Socket 与线程练习。[tests](../tests/)放断连和描述符复用回归。

## 单元 19 的验收顺序

1. 先让同一轮网关接入两条 TCP 连接。A 请求不存在的设备地址，确认客户端收到可区分的超时或网关异常。随后让 B 请求设备 1，确认合法请求仍得到正确回复。
2. 用可控的沉默后端复现已发送串口请求但设备没有回复的场景。让客户端先看到网关返回的结果，并单独观察网关日志。每项实验先明确初始状态和期望输出。
3. 区分两个时间段：连接线程提交后到工作线程取走的排队时间，以及工作线程发出请求后等设备回复的时间。需要配置超时时再复习 `modbus_set_response_timeout()` 的参数和返回值。
4. 记录实际观察到的异常码、退出状态和下一条请求结果。根据实际复测再调整代码与验收状态。

## 已积累的经验

| 场景 | 已验证的做法 |
|---|---|
| make 找不到源文件 | 核对终端目录、Makefile 依赖的文件名、编辑器实际保存路径。主站曾保存成带空格的命令名，改名后构建成功 |
| 构建成功却跑不起来 | 执行 `build/` 下的程序。提示 Nothing to be done 表示已有产物可复用 |
| TCP 已连上却读写超时 | 按连接目标和监听端口追踪请求。单客户端代理实验中，1502 是模拟设备、1503 是代理；共享后端网关的入口是 1506 |
| 连接失败与设备异常 | Connection refused 发生在连接阶段。Illegal data address 来自设备的异常回复；即使设备拒绝操作，代理也可能成功转发这条回复 |
| 后端沉默 | 先确认请求已到达后端，再扣住回复。20 ms 和 200 ms 分别是 20000 与 200000 微秒 |
| 缓冲区重用 | 队列中的请求保存独立的字节和长度。后端线程取出任务后解锁，再执行转发 |
| 客户端在途断开 | 请求、前端上下文和连接在后端使用期间保持有效。工作线程完成后再释放；文件描述符编号可以被后来连接复用 |
| 区分端点和地址 | 串口路径决定打开哪个 Linux 设备端点；9600 8N1 是串口参数；Unit ID 选择 Modbus 设备；寄存器地址选择设备里的数据 |

## 教学和协作约定

1. 开始一节时先给当前项目中的具体功能和验收标准，再讲这一步需要的前置知识。
2. 函数速查讲清楚调用方式、参数、返回值和用途，然后带着问题看现有代码。C 函数调用与返回值判断分开写。
3. 先跑通最小实现，再用观察到的失败说明为何需要锁、超时、检查或清理。示例围绕项目已有的真实请求和路径展开。
4. 用户负责理解关键路径和复现，助手可配置环境、做重复性更改和联调。记录里分清用户亲手验证与助手代跑。
